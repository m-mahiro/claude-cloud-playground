DOM への重複アクセスは大きく減った

DOM API を包み、要素ごとに「どのスクリプト(CP Toolkit は機能)が、取得・読み取り・書き換えを何回したか」を数えました。旧スクリプトでは、同じ要素を別々のスクリプトがそれぞれ探し直しています。CP Toolkit ではそれが機能の間でも少なく、書き込み直後にレイアウトを読む処理(強制レイアウトの疑い)もなくなりました。

ページ全体で見ると、差はばらつきに埋もれる

CDP の Performance.getMetrics で、ページのメインスレッドが使った時間(TaskDuration)を測りました。スクリプトなしとの差を UserScript による増分としています。ページ自体の処理が大きく、ばらつき(スクリプトなしでの四分位範囲 —〜— ms)が UserScript の差と同じくらいあるため、ほとんどのページで統計的な差は出ていません。

測り方と限界

  • 旧スクリプトは、nsubaru 版8本の統合前の最終版(コミット 7c4fc38 の直前)と、SOURCES.md で「派生」「模倣」の元になった公開スクリプト18本。Chrome 拡張の2つ(Statement Lens、comfortable-atcoder)は含めていません。CP Toolkit は 1.0.26。
  • ページは AtCoder の公開ページ9つを一度だけ録画し、計測ではそれだけを返しました。提出一覧・順位表・提出画面はログインが必要なため対象外で、提出まわりの機能(結果の平均、検索条件の保持など)は測れていません。
  • 最初の節だけは実際の Tampermonkey 5.5.1 で測りました。ほかの節は、Tampermonkey の代わりに全条件で同じ軽いシムを使っています(@match・@run-at・@require に従って起動)。シムでは Tampermonkey 自身の負荷が入らないので、本数を減らす効果は最初の節にしか出ません。
  • 環境はクラウドの Linux 上の headless Chromium です。絶対値より、条件の間の差を見てください。
  • DOM の計測は API を包んで数えたもので、時間の計測とは別の回です。children などの辿り方は数えていません。
  • 計測コードと手順: github.com/m-mahiro/claude-cloud-playground の perf-cptoolkit。
